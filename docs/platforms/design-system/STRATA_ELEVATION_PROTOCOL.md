# Strata Elevation Protocol v1.0

Status: frozen procedure text for bounded component packets, 2026-09-26; **mass execution activation withheld until all three calibration packets meet the PASS rule**. Owner: PLT-DS. This protocol implements [Design Platform requirements](REQUIREMENTS.md), [experience](EXPERIENCE.md), [architecture](ARCHITECTURE.md), [package contract](CONTRACTS.md), and ADR-0009. The linked evidence ledger records the calibration run; it does not certify the entire catalog.

## Fixed decisions

1. Preserve Inter headings/body/data, IBM Plex Mono only for identifiers and code, Lucide icons, Strata Neutral/Nova restraint, semantic tokens, default 6–8px control radius, four density tiers, and `strata`, `strata-dark`, `strata-high-contrast` themes. Do not import a reference's Tailwind theme, font, colour or package wholesale.
2. L1 Design Platform owns reusable presentation, semantics and behavior; apps own data, domain rules, persistence and permission decisions. Storybook is an L4 consumer. The global StrataBar context is a shell responsibility; a local Breadcrumb may show a subordinate hierarchy but must not create a second global context trail.
3. Within this package major, preserve supported exports, prop meanings and token names. A behavioral or contract break is a new-major decision requiring named consumers, migration, rollback and exact owner approval.
4. Use the existing five-file anatomy (`.tsx`, `.module.css`, `.stories.tsx`, `.test.tsx`, `index.ts`), public package subpaths, token gates and component inventory. Search semantic equivalents before creating a component.

## Repeatable packet, in dependency order

For each element, record a unique packet ID and execute these stages in order. Do not mark a stage complete from file presence.

1. **Authority and baseline.** Read current ADR, owning requirement/experience/contract, repository instructions, nearby component, exports, token sources, tests, stories, consumers and working diff. Record source revision, risk class, owner and numbered acceptance criteria. Protect unrelated edits.
2. **Identity and necessity.** State user job, anatomy, public API, variants, states, theme/density behavior, dependencies, consumers, keyboard/screen-reader behavior and architectural layer. Search by meaning across components and applications. Classify `KEEP`, `MERGE`, `DEPRECATE` or `REMOVE-CANDIDATE` with evidence.
3. **Component-specific research.** Search official shadcn/ui docs and registry/directory first, then shadcn dashboard and registry ecosystem (Shadcn Dashboard, Studio, Admin, UI Kit, Space, Blocks, Templates, Store, shadcn.io), 21st.dev, Origin UI, ReUI, Magic UI, Aceternity UI and enterprise admin/ERP template sources. Inspect at least three *actual equivalents* where available, not just catalog landing pages. Record URL, inspection date, exact relevant state and behavior, license/dependency cost, accessibility evidence and limitations. An inaccessible/paywalled or marketing-only example is context, not a verified implementation.
4. **Benchmark selection.** Score each equivalent 0–3 on task fit, interaction completeness, state coverage, density/responsive behavior, semantics/keyboard, visual discipline, code portability and maintenance. Weight task fit and semantics twice; reject any reference with a critical keyboard/contrast failure regardless of score. Choose one primary benchmark and at most two supplemental references for distinct traits. Record why each trait beats the current Strata behavior and what is deliberately rejected. Source markup is evidence, not a copy target.
5. **Change contract.** For R2/R3, write acceptance criteria, owner/consumer graph, invariants, compatibility, failure/recovery, planned checks and knowledge delta before mutation. Update intended shared behavior first when it changes. Resolve duplications by convergence, never add a third implementation.
6. **Implementation.** Modify the canonical element in place. Keep native HTML semantics and labels, unique names for repeated landmarks, focus visibility, live state, logical CSS properties, semantic tokens, typed callbacks and deterministic keys. Do not dim disabled text by opacity on top of an already-muted semantic colour; inspect the rendered state. Use controlled state for business results; do not announce success before the consumer confirms it. For existing synchronous callbacks whose behavior is already public, preserve semantics. If an interaction needs pending/accepted/rejected states without a breaking change, add a typed opt-in confirmation callback; show pending feedback, await the result, catch rejection, retain parent-provided data as authority and expose an accessible result. A rejection must never commit a local display value or re-submit merely because focus returns. Preserve component anatomy and add real state stories and behavior tests that would fail on regression. No new dependency without the supply-chain review.
7. **Provider gates.** Run focused unit/interaction/axe tests, then token/contrast/density/logical-property, inventory, Storybook, typecheck, lint, full test and build gates from the current manifest. Record command, exit code and target count. A zero-target, skipped, stale, partial or environment-blocked gate is not PASS.
8. **Browser comparison.** In the real Storybook browser, render the local story and selected reference at comparable viewport. Exercise default, hover, focus, disabled/read-only/invalid/loading/empty/selected/edit/error states as applicable; three canonical themes; all four densities; narrow and wide widths; LTR and RTL; keyboard and focus exit; 200% zoom/reflow; reduced motion and forced colours. Use a full matrix for critical data/interaction controls and documented pairwise coverage for lower-risk primitives. Inspect visual hierarchy, size, wrapping, contrast, scroll affordance and accessible names/states. Record screenshot or browser observation bound to story URL, revision, viewport, theme, density, direction and state. Automated axe plus keyboard plus a representative screen-reader check are required before accessibility PASS.
9. **Consumers and handoff.** Validate published subpath/package behavior, then affected consumer builds/tests and at least one real journey. Run upstream first. Review the complete diff, record failures and pre-existing debt separately, update traceability/evidence, and give a structured downstream handoff. Never call an unverified consumer integrated.

## Quality checklist and PASS/FAIL rule

An element passes only if its necessity and owner are established; the reference decision is source-backed; all supported states and variants render coherently in Strata themes/densities; keyboard and accessible semantics work; responsive/RTL/high-contrast evidence exists; focused and package gates pass; affected consumers pass; no critical regression remains; and the final diff/evidence ledger is reviewed. Every item is binary `PASS`, `FAIL`, `BLOCKED` or `NOT VERIFIED`. A missing required item makes the element `NOT VERIFIED` or `FAIL`, never PASS. A single benchmark is never a blanket design mandate for another element. A pleasing screenshot without interaction evidence fails.

For visual comparison, prefer readable aligned surfaces, clear hierarchy and visible state over ornament. Check label-to-control association, unique landmark names when stories/pages render repeated components, text/focus/control contrast including disabled and placeholder states, no colour-only state, no clipped text/action, tabular numbers in data, appropriate 24/28/32/40px row rhythm, comfortable 44px target, and 200% reflow. A grid may scroll horizontally only with a named keyboard-reachable region and an accessible small-screen alternative.

## Merge and removal rule

When two components share purpose, first map public exports and exact consumers. Designate the higher-authority canonical implementation, record the other as an adapter or deprecated alias, and provide a one-to-one prop/state mapping. Keep the old import usable in the current major; migrate consumers by owner with equivalent keyboard, visual and API evidence. Instrument usage or generate an import inventory and require zero active consumers, expiry window, rollback and owner approval before major-version removal. Do not delete a duplicate because a grep count is zero or because its appearance is similar. For this calibration, `core/primitives/input/Input` remains the public root Input; `core/inputs/form-control/Input` overlaps but has `invalid`, `prefixIcon`, and `suffixIcon` props. A future adapter maps them respectively to `error`, `leftIcon`, and `rightIcon`; preserves native attributes/ref, the form-control subpath, and `TextField` composition; and is verified against exact app imports before marking the legacy export deprecated. No removal is authorized here.

## Evidence ledger format

One row per criterion and browser matrix sample:

`packet-id | source-revision | component/export | criterion | reference URL and trait | local story/route | viewport/zoom | theme | density | direction | state/input action | visual observation | AX/keyboard/axe/screen-reader result | command/check and target count | consumer/result | PASS/FAIL/BLOCKED/NOT VERIFIED | issue/fix/owner | date`

Store dated records in `evidence/`, not in this normative protocol. Bind screenshots to an actual build/revision; rerun when code changes. List every required but unrun dimension explicitly. Approval or release is never inferred from this ledger.
