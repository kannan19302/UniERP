# Finance current-state audit — 10 September 2026

## Decision and scope

**Finance needs a reliability and workflow consolidation program before a visual-polish program.** The current UI contains useful enterprise patterns, but it can present failed requests as healthy financial results, exposes inconsistent workflow entry points, and has serious responsive-layout problems. Source inspection also identifies simulated accounting behavior behind some redesigned screens.

This is dated advisory evidence, not an accepted architecture decision, production certification, or authorization to implement. Scope: all 90 Next.js finance route files were inventoried and scanned; selected shared components, resource definitions, controllers, services, contracts, schema and tests were inspected more deeply. Seven routes were sampled in an authenticated local browser. This is **not** a completed transactional end-to-end or full accessibility audit.

Deliverables: this findings report, [the detailed master improvement prompt](FINANCE_MASTER_IMPROVEMENT_PROMPT_2026-09-10.md), and the generated screen inventory linked from that prompt. The prompt separates proposed behavior from inspected implementation.

Risk: R0 analysis; R1 local evidence documents. Future implementation spans R2 and sometimes R3. Owners: PLT-ERP experience/product; PLT-BIZ finance domain, API, persistence and contracts; PLT-DS shared UI; PLT-IAM permissions and identity; PLT-OPS deployed-build evidence. Inspected repositories: tenant-apps, api, data, unierp-contracts, unierp-platform, and relevant workspace governance. Only evidence documents are changed by this audit.

Snapshot: tenant-apps HEAD `2f1b7e750af1d51dbeecb710d4b565f0b7e8ee49`; api HEAD `3ee64e2779e050961d0e2f31002adca69199f826`. Tenant-apps already contained many modified and untracked finance, shell, export and keyboard files. Findings include that working tree; the commit alone does not reproduce it. No existing changes were overwritten.

## Architecture and runtime discrepancy

The running local GL endpoint returned 404 even though the current source declares that endpoint. The sampled AP summary, asset summary and budget summary endpoints also returned 404. The local dashboard, invoice lists and advanced account-list endpoint returned 200. Therefore, the source service’s fallback/journal behavior is a **source finding**, not behavior demonstrated by posting in the running app. Verify process routing, proxy configuration, compiled API revision, controller registration and active build before concluding which version is deployed. Do not “fix” a 404 by adding fake client data.

## Consistency standard

Use UniERP’s PLT-DS and ERP experience specifications as authority. SAP and Microsoft provide pattern benchmarks, not a mandate to copy branding, adopt their libraries, or claim feature parity.

- Use stable list-to-record workflows for filtering, scanning and inspecting objects, consistent with [SAP’s list report and object-page guidance](https://help.sap.com/docs/SAPUI5/b2f662dd9d7a4ec680056733050b4d34/c0eec49db81a441e878f528c8f3d28de.html?version=1.147).
- Make close tasks accountable and visible by schedule and assignee, following the workflow principle documented for [Dynamics 365 financial period close](https://learn.microsoft.com/en-us/dynamics365/finance/general-ledger/financial-period-close-workspace).
- Verify WCAG 2.2 AA, including keyboard access, unobscured focus, target sizing, error identification and financial error prevention. See [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/). Compact row height alone does not establish target-size conformance.

Tax thresholds, filing formats and named accounting standards in the product are not certified by this audit. Proposals require jurisdiction/effective-date ownership and appropriate accounting review, not hardcoded assumptions derived from page labels.

## Useful foundations to retain

The shared resource framework already provides tables, filtering and some saved-view capabilities. The chart of accounts and invoices rendered actual API-backed lists locally. An advanced workspace catalog exists. The invoice detail uses a shared TransactionWorkspace; several advanced workflows use shared dialogs, RouteGuard and published specialized contracts. Finance SubTabBar is a re-export of the design-system component. Preserve these reusable foundations while aligning their contracts and behavior. An API response or shared component alone still does not prove end-to-end correctness.
